## What I built

A FastAPI backend skeleton (the FastAPI alternative named in `backend/README.md`)
wired for async PostgreSQL access. `config/settings.py` is a `pydantic-settings`
schema that reads every value from the environment; `config/database.py` creates
the async SQLAlchemy engine, session factory, and the `get_db` FastAPI dependency;
`config/main.py` is the application entrypoint with CORS, a standardized JSON error
envelope (`config/exceptions.py`), and a lifespan hook that verifies the database is
reachable on startup. `GET /api/v1/health` and `GET /api/v1/health/db` give a
reviewer an immediate liveness/connectivity check.

On the data side, all seven tables from the spec are modelled as SQLAlchemy 2.0
declarative models, placed into the existing per-module app folders rather than a
fresh layout: `apps/accounts` (`User`, `CaregiverPatientMapping`), `apps/profiles`
(`UserProfile`), `apps/medications` (`Medicine`), `apps/reminders` (`Reminder`),
`apps/adherence` (`AdherenceLog`), and `apps/refills` (`RefillLog`). Shared UUID and
timestamp mixins, the declarative `Base`, and cross-app enums live in `apps/common`
to avoid the import cycles that app's README warns about.

Two bugs surfaced and fixed along the way, worth calling out for reviewers: (1) the
shared `backend/pyproject.toml` had an unescaped backslash in the Black config that
made the file invalid TOML — this would have broken `pytest`/`black`/`isort` for
every branch, not just mine, and is fixed with a literal TOML string instead of an
escaped one; (2) Alembic's autogenerated `downgrade()` dropped tables but left
PostgreSQL's native ENUM types behind, so a downgrade-then-upgrade cycle failed with
`DuplicateObjectError`. Fixed by adding explicit `sa.Enum(...).drop(bind,
checkfirst=True)` calls at the end of `downgrade()` — verified with a real
up/down/up/down/up cycle against a live Postgres instance, not just a read-through.

## Database design

See `docs/database/` for the ER diagram (same one from the project spec). Summary of
the seven tables and their relationships:

- **`users`** — one row per account (`PATIENT` / `CAREGIVER` / `ADMIN`); central FK
  target for almost everything else.
- **`user_profiles`** — 1:1 with `users`; health/personal details kept out of the
  identity table on purpose.
- **`caregiver_patient_mapping`** — many-to-many between caregivers and patients
  (two FKs into `users`), with an access level and a pending/accepted/rejected
  status.
- **`medicines`** — owned by a `user`; carries the stock fields (`total_quantity`,
  `remaining_quantity`, `refill_threshold`) the refill engine will read in
  Milestone 3.
- **`reminders`** — belongs to a `medicine` and (denormalized, per the spec) a
  `user`; scheduled time and frequency.
- **`adherence_logs`** — one row per Taken/Missed/Snoozed event against a
  `reminder`.
- **`refill_logs`** — one row per stock top-up against a `medicine`.

Every FK uses `ON DELETE CASCADE`, and every PK is an app-generated UUID
(`sqlalchemy.Uuid`, not `postgresql.UUID`) so the same models can run against
SQLite in fast unit tests and PostgreSQL in production/CI without dialect-specific
branching.

## How to run and verify it

```bash
# 1. Start Postgres (and redis, for later milestones) via Docker, or point
#    backend/.env at your own local Postgres instance.
cp backend/.env.example backend/.env   # then fill in a real SECRET_KEY
docker compose up --build db redis

# 2. Install dependencies and apply migrations.
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements/dev.txt
alembic upgrade head

# 3. Run the app.
uvicorn config.main:app --reload

# 4. Verify.
curl http://localhost:8000/api/v1/health       # {"success": true, "data": {"status": "ok"}}
curl http://localhost:8000/api/v1/health/db    # {"success": true, "data": {"database": "reachable"}}
open http://localhost:8000/docs                # Swagger UI

# 5. Round-trip the migration to confirm it's reversible.
alembic downgrade base
alembic upgrade head
alembic check                                  # "No new upgrade operations detected."
```
